# Feature Specification: Этап 0.1 «Исполнение» — запуск задачи оператором и её исполнение движком

**Feature Branch**: `feat/t-003-execution-stage`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "Continue where you left off" — продолжение дорожной карты проекта: фича 001 — этап 0.1 «Исполнение» (`docs/analysis/2026-09-22-init-architecture-comparison.md` §9, шаг 4; ADR-0009 стадия 0.1): CLI → адаптер → DSH → результат.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Оператор запускает задачу и получает результат исполнения (Priority: P1)

Оператор фабрики запускает задачу (изменение продукта) одной командой и получает
подтверждение запуска с идентификатором. Фабрика исполняет задачу агентной попыткой
во внешнем движке исполнения (DSH) и сохраняет результат. По завершении оператор
видит итог попытки: что сделано, какие артефакты созданы, чем закончилась попытка
(выполнено / неудача / прервано / отменено).

**Why this priority**: это фундамент фабрики — без исполняемой попытки с результатом
не имеют смысла остальные стадии (процесс, гейты, доставка). Единственный сквозной
сценарий стадии 0.1.

**Independent Test**: полностью проверяется одной командой запуска и просмотром
итога после завершения попытки; доставляет ценность «задача исполнилась, результат
зафиксирован».

**Acceptance Scenarios**:

1. **Given** фабрика настроена и доступен движок исполнения, **When** оператор запускает
   задачу с описанием работ, **Then** он получает подтверждение с идентификатором задачи
   и запуска, а задача переходит в состояние «исполняется».
2. **Given** задача исполняется, **When** попытка завершается успешно, **Then** фабрика
   фиксирует итог `completed` с артефактами попытки и отчётом агента, и оператор видит
   завершённый результат.
3. **Given** задача исполняется, **When** попытка завершается неудачей, **Then** фабрика
   фиксирует итог `failed` с описанием ошибки, отличая повторимую ошибку от
   неповторимой.
4. **Given** ядро фабрики перезапустилось во время исполнения, **When** оператор
   запрашивает состояние, **Then** фабрика показывает актуальное состояние задачи и
   попытки без потери записи о запуске.

### User Story 2 - Оператор наблюдает состояние в любой момент (Priority: P2)

В любой момент исполнения оператор запрашивает состояние и видит: идентификаторы
задачи/запуска/этапа/попытки, текущее состояние (`pending, ready, running,
waiting_input, reconciling, evaluating, accepted, blocked, failed, cancelled`),
ход попытки (снимок исполнения из движка) и уже зарегистрированные артефакты.

**Why this priority**: без наблюдаемости оператор не может понять, что происходит
с запущенной задачей; это вторая по значимости ценность стадии 0.1.

**Independent Test**: запустить долгую задачу, в процессе запросить состояние —
получить согласованный снимок; доставляет ценность «я вижу, что происходит».

**Acceptance Scenarios**:

1. **Given** задача исполняется, **When** оператор запрашивает статус, **Then** он видит
   состояние задачи, этапа и попытки, соответствующее реально исполняемой работе.
2. **Given** попытка ждёт события от движка, **When** оператор запрашивает статус,
   **Then** фабрика отражает состояние ожидания (`waiting_input` / `reconciling`),
   а не «исполняется».
3. **Given** попытка завершилась, **When** оператор запрашивает статус, **Then** он видит
   финальный итог и список артефактов с идентификаторами.

### User Story 3 - Оператор отменяет запущенную задачу (Priority: P3)

Оператор может отменить запущенную задачу. Фабрика передаёт отмену в движок,
останавливает дальнейшее исполнение и фиксирует итог `cancelled`. Уже выполненные
внешние действия не откатываются (автооткат запрещён).

**Why this priority**: управляемость — оператор должен уметь остановить ошибочный
или ненужный запуск; без отмены стадия 0.1 небезопасна в использовании.

**Independent Test**: запустить задачу, отменить её, убедиться что дальнейшее
исполнение остановлено и итог `cancelled`; доставляет ценность «я управляю запуском».

**Acceptance Scenarios**:

1. **Given** задача исполняется, **When** оператор отменяет её, **Then** фабрика
   запрашивает отмену попытки в движке и фиксирует итог `cancelled`.
2. **Given** попытка уже завершилась, **When** оператор отменяет задачу, **Then** фабрика
   не меняет зафиксированный итог попытки (отмена не переписывает завершённый результат).
3. **Given** отмена запрошена, **When** движок подтверждает остановку, **Then** новые
   попытки задачи не запускаются.

### User Story 4 - Повторные команды безопасны (идемпотентность) (Priority: P4)

Повторная отправка той же команды (запуск, отмена, ответ) с тем же идентификатором
команды и тем же содержимым возвращает прежнюю квитанцию и не создаёт дублей.
Та же команда с изменённым содержимым — явный конфликт. Повторный запуск попытки
с тем же ключом исполнения и другим содержимым — конфликт.

**Why this priority**: защищает от дублей при сетевых повторах и повторных нажатиях;
важно для надёжности, но реализуется поверх историй 1–3.

**Independent Test**: отправить одну и ту же команду дважды с одним идентификатором —
получить одну квитанцию и ровно один запуск.

**Acceptance Scenarios**:

1. **Given** команда запуска принята, **When** та же команда (тот же идентификатор,
   то же содержимое) приходит повторно, **Then** фабрика возвращает прежнюю квитанцию,
   дубль задачи не создаётся.
2. **Given** команда принята, **When** та же команда приходит с изменённым содержимым,
   **Then** фабрика отклоняет её с явным конфликтом.
3. **Given** попытка запущена с ключом исполнения, **When** повторный старт с тем же
   ключом, но другим содержимым, **Then** фабрика фиксирует конфликт и не запускает
   вторую попытку.

### Edge Cases

- Что происходит, когда движок исполнения недоступен в момент запуска? — фабрика
  фиксирует попытку в состоянии «запускается» с ошибкой, помечая её повторимой, и
  оператор может повторить запуск (технический повтор, не новая работа).
- Что происходит при обрыве связи с движком во время исполнения (`interrupted`)? —
  фабрика фиксирует состояние «прервано» и не делает слепых повторов; возобновление —
  осознанное действие оператора (`resume`).
- Что происходит, когда результат движка неоднозначен (неизвестно, выполнилась ли
  внешняя операция)? — фабрика фиксирует внешнюю операцию как `unknown`, который
  блокирует слепой повтор, и показывает её оператору.
- Что происходит при отмене в момент, когда движок ещё отвечает «исполняется», но
  фактически уже завершился? — фабрика сверяет факт (`reconciling`) и фиксирует
  фактический итог, не подменяя его отменой.
- Что происходит при попытке ответить на вопрос устаревшей версии? — фабрика
  отклоняет ответ с указанием актуальной версии вопроса (в 0.1 — если вопрос
  возник в попытке; полный контур вопросов — стадия 0.2).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST позволять оператору запустить задачу одной командой (`df start`)
  с указанием описания работ и вернуть подтверждение с идентификаторами задачи и запуска.
- **FR-002**: Система MUST исполнять задачу агентной попыткой во внешнем движке
  исполнения через адаптер: одна попытка соответствует одной сессии движка.
- **FR-003**: Система MUST фиксировать итог попытки одним из: `completed | failed |
  cancelled | interrupted` — и хранить его неизменным после завершения попытки.
- **FR-004**: Система MUST сохранять артефакты попытки по протоколу
  `temp → validate → rename → register` и связывать их с попыткой.
- **FR-005**: Система MUST позволять оператору в любой момент запросить состояние
  задачи (`df status`): идентификаторы, состояния задачи/этапа/попытки, снимок
  исполнения, зарегистрированные артефакты.
- **FR-006**: Система MUST отражать состояния этапа `pending → ready → running →
  (waiting_input | reconciling) → evaluating → accepted | blocked | failed | cancelled`;
  на стадии 0.1 исход `accepted` присваивается только при явном ручном принятии
  результата оператором (полноценные гейты — стадия 0.2).
- **FR-007**: Система MUST отличать повторимые ошибки (`error.retryable`) от
  неповторимых и не делать слепых технических повторов без явного действия оператора
  (`resume`).
- **FR-008**: Система MUST позволять оператору отменить запущенную задачу (`df cancel`)
  с фиксацией итога `cancelled`, не переписывая итог уже завершённой попытки.
- **FR-009**: Система MUST гарантировать идемпотентность команд по `commandId`:
  same+same → прежняя квитанция; same+diff → конфликт.
- **FR-010**: Система MUST фиксировать неоднозначные внешние операции как `unknown`,
  блокирующие слепой повтор, и показывать их оператору.
- **FR-011**: Система MUST переживать перезапуск ядра без потери записей о запущенных
  задачах и попытках (состояние — единственный владелец фабрики; второй процесс
  `run/resume` подключается к владельцу, параллельных писателей нет).
- **FR-012**: Система MUST ограничивать попытку лимитами из запроса исполнения
  (время, число запросов к модели, стоимость) и фиксировать фактическое потребление.
- **FR-013**: Система MUST хранить структурированный отчёт агента по завершении попытки
  (итог работы, использованные артефакты, ссылки на сессию).
- **FR-014**: Система MUST поддерживать технический повтор запуска (`retry`) отдельно
  от циклов доработки: технический повтор возобновляет ту же попытку, доработка
  (новая попытка по результатам проверки) — вне стадии 0.1.

### Key Entities *(include if feature involves data)*

- **Change** — задача (изменение продукта): описание работ, идентификатор; запускается
  оператором.
- **Run** — прогон процесса по Change: состояния `created, running, waiting, succeeded,
  failed, cancelled`.
- **StageRun** — исполнение одного этапа внутри Run; имеет номер поколения
  (`generation`); состояния из FR-006.
- **Attempt** — агентская попытка (одна попытка = одна сессия движка исполнения);
  ключ исполнения (`executionKey`), снимки исполнения, итог из FR-003, usage/лимиты.
- **Artifact** — результат попытки: идентификатор, расположение, контрольная сумма,
  тип; регистрируется по протоколу FR-004.
- **ExternalOperation** — выполненное во внешней системе действие: `prepared / unknown`.
- **CommandReceipt** — квитанция операторской команды: идентификатор команды (`commandId`),
  результат приёма; основа идемпотентности FR-009.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор запускает задачу одной командой и получает подтверждение с
  идентификаторами не более чем за 30 секунд от ввода команды (при доступном движке).
- **SC-002**: В 100% повторов одной и той же команды с тем же идентификатором фабрика
  возвращает одну и ту же квитанцию — 0 дублирующихся задач/попыток.
- **SC-003**: В 100% завершённых попыток итог (`completed/failed/cancelled/interrupted`)
  зафиксирован и доступен оператору в статусе, включая случаи перезапуска ядра
  во время исполнения.
- **SC-004**: Оператор получает актуальное состояние задачи в любом состоянии её
  жизненного цикла — время ответа на запрос статуса не превышает 2 секунд при
  локально доступном хранилище.
- **SC-005**: Отмена останавливает дальнейшее исполнение в 100% случаев, когда движок
  подтверждает остановку; итог уже завершённой попытки не изменяется ни в одном случае.
- **SC-006**: Неоднозначные внешние операции (0 в идеале) в 100% случаев маркируются
  `unknown` и блокируют слепой повтор — ни одной незамеченной неоднозначности.

## Assumptions

- Оператор — единственный пользователь стадии 0.1; работа ведётся локально на машине
  фабрики через CLI (без веб-интерфейса; Console — после MVP).
- Движок исполнения (DSH) уже доступен и настроен: у фабрики есть доступ к нему через
  его интерфейс; учётные данные не хранятся в репозитории (ссылки, подстановка в момент
  исполнения).
- На стадии 0.1 процесс фиксированный и минимальный: один этап исполнения; граф этапов,
  декларативные описания и гейты — стадии 0.2–0.3.
- Ручное принятие результата оператором (перевод этапа в `accepted`) — минимальная
  замена гейта на этой стадии; формальные проверки и доработка — стадия 0.2.
- Ограничения параллельности (лимиты одновременных попыток, очереди) — стадия 0.5;
  на 0.1 предполагается один активный запуск за раз.
- Доставка, merge и работа с VCS — вне стадии 0.1 (стадия 0.6); попытка не отправляет
  код в продуктовый репозиторий.
- Изоляция попытки — локальный воркспейс (worktree-режим); контейнеры и удалённые
  исполнители — позже.
- Восстановление после сбоя ядра опирается на хранилище состояния фабрики; резервное
  копирование — по ADR-0002 (backup вместо rebuild).
