# Requirements Quality Checklist: Этап 0.1 «Исполнение»

**Purpose**: проверка качества спецификации этапа 0.1 — полнота, однозначность,
проверяемость требований перед переходом к планированию (`/speckit-clarify` →
`/speckit-plan`).
**Created**: 2026-09-22
**Feature**: [specs/001-execution-stage/spec.md](../spec.md)

**Note**: Этот чек-лист сгенерирован в рамках `/speckit-specify` (встроенный
проверочный проход по шаблону `requirements`); отдельный вызов `/speckit-checklist`
не выполнялся.
**Review Ownership**: чек-лист — ревью-артефакт качества требований. Пункт `[x]`
проставляется только когда критерий реально удовлетворён спецификацией.
**Marker Semantics**: `[x]` — критерий проверен и удовлетворён на уровне требований.
Это не означает завершение реализации.

## Content Quality

- [x] CHK001 Спецификация формулирует ясную цель, привязанную к потребности
      (US1 «Why this priority»: без исполняемой попытки не имеют смысла остальные
      стадии; источник — дорожная карта §9 шаг 4, ADR-0009 стадия 0.1).
- [x] CHK002 Каждая user story имеет явный приоритет и независимую проверяемость
      (P1–P4, у каждой — блок «Independent Test»).
- [x] CHK003 Критерии успеха измеримы и привязаны к сценариям (SC-001…SC-006:
      время подтверждения ≤30 с, 0 дублей, 100% фиксации итогов, ответ статуса ≤2 с).
- [x] CHK004 Границы скоупа заданы: вне стадии 0.1 явно названы гейты (0.2),
      декларативные процессы (0.2–0.3), параллельность (0.5), доставка/merge (0.6)
      — см. Assumptions.

## Requirement Completeness

- [x] CHK005 Все функциональные требования сформулированы с MUST и проверяемы
      (FR-001…FR-014).
- [x] CHK006 Краевые случаи перечислены и для каждого задано поведение системы
      (5 случаев: недоступность движка, обрыв связи, неоднозначный результат,
      отмена при гонке завершения, устаревший ответ на вопрос).
- [x] CHK007 Маркеров `[NEEDS CLARIFICATION]` и плейсхолдеров нет.
- [x] CHK008 Ключевые сущности определены с состояниями и жизненными циклами
      (Change, Run, StageRun, Attempt, Artifact, ExternalOperation, CommandReceipt;
      состояния из FR-003/FR-006).
- [x] CHK009 Альтернативные и ошибочные пути описаны как требования, а не только
      в сценариях: итоги `failed/cancelled/interrupted` (FR-003), повторимые/
      неповторимые ошибки и запрет слепых повторов (FR-007, FR-010), отмена без
      перезаписи итога (FR-008).
- [x] CHK010 Нефункциональные ограничения зафиксированы проверяемо: лимиты попытки
      (время, запросы к модели, стоимость — FR-012), тайминги (SC-001, SC-004),
      переживание перезапуска ядра (FR-011, SC-003).

## Feature Readiness

- [x] CHK011 Сценарии приёмки каждой user story записаны в форме Given/When/Then
      (по 3–4 сценария на историю).
- [x] CHK012 Требования не навязывают реализацию: названы команды CLI и доменные
      протоколы (`temp → validate → rename → register`), но не выбраны язык,
      фреймворк или схема хранения (владелец состояния по ADR-0002 — уровень plan).
- [x] CHK013 Каждое FR прослеживается до user story или краевого случая:
      FR-001/002/003/004/011/012/013 → US1 (запуск, исполнение, итог, переживание
      перезапуска); FR-005 → US2; FR-006 → US2 (сценарий 2) и Assumptions (ручное
      принятие); FR-008 → US3; FR-009 → US4; FR-007/FR-014 → US4 и краевой случай
      про недоступность движка; FR-010 → краевой случай про неоднозначный результат.
- [x] CHK014 Терминология согласована с глоссарием HLD и ADR (итоги попытки
      `completed/failed/cancelled/interrupted`, состояния этапа `waiting_input/
      reconciling/evaluating…`, `unknown` для внешних операций, `retry ≠ rework`).
- [x] CHK015 Критерии успеха проверяемы без реализации (измеримые величины и
      условия, воспроизводимые сценариями из user stories).
