# Git-цикл задачи

Штатный порядок выполнения любой задачи, меняющей файлы репозитория (код, тесты,
документация, конфиги). Цикл обрамляет реализацию: роль `ci-cd` подключается в начале
(ветка) и в конце (MR), merge остаётся за человеком. Кратко — `AGENTS.md`.

## Шаги

| # | Шаг | Роль | Действие | Результат |
|---|---|---|---|---|
| 1 | Ветка | `ci-cd` | Синхронизировать `main` и создать от него ветку задачи, запушить | Ветка задачи в origin |
| 2 | Реализация | `develop` | Внести минимальные изменения в ветке задачи | Коммиты в ветке |
| 3 | Проверка | `develop` | Фактически запустить `pnpm build`, `pnpm test`, диагностику по изменённым файлам | Зелёные проверки + evidence |
| 4 | MR | `ci-cd` | Закоммитить, запушить и открыть MR против `main` с описанием и evidence | Открытый MR |
| 5 | Merge | человек | Ревью и merge | Merge в `main` |

Реализация не начинается до создания ветки (шаг 1) и не считается завершённой до
открытия MR (шаг 4). CI повторяет проверки шага 3 на самом MR — подключается на
этапе 0.2+ (ADR-0009); до того шаг 3 — единственный источник evidence.

Merge в `main` — только человек. Автономный merge появится позже и только для
продуктовых репозиториев, при выполнении 5 условий и политик риска
(ADR-0006, ADR-0012/Q9).

## Trunk-based development

Модель ветвления — trunk-based: ветка задачи короткоживущая, ответвляется от
свежего `main`, живёт ровно одну задачу и вливается обратно только через MR
(merge — человек). Долгоживущих веток разработки нет; `main` всегда стабилен и
готов к релизу. Если работа не влезает в одну задачу — дроби её, а не держи
ветку открытой.

## Именование веток

`<type>/t-NNN-<slug>`, где `NNN` — номер задачи, `slug` — короткий английский
идентификатор:

- `feat/t-001-core-domain` — новая функциональность;
- `fix/t-007-gate-verdict` — исправление;
- `chore/…`, `docs/…`, `refactor/…`, `test/…` — по характеру задачи.

`main` всегда стабилен: push в него напрямую запрещён.

## Команды

**Шаг 1 — ветка (`ci-cd`):**

```sh
git fetch origin --prune
git checkout main
git pull --rebase origin main
git checkout -b feat/t-<NNN>-<slug>
git push -u origin feat/t-<NNN>-<slug>
```

**Шаг 4 — MR (`ci-cd`):**

```sh
git add <файлы задачи>
git commit -m "feat: <описание> (t-<NNN>)"
git push -u origin HEAD
```

MR/PR открывается в VCS-провайдере (GitHub-first — Q4/ADR-0012; GitLab — второй
provider за тем же контрактом VCS Provider, ADR-0006) с описанием изменения,
затронутыми ADR и evidence шага 3.

## Секреты в цикле

Значения секретов не попадают в коммиты, MR-описания и логи: в коде и декларациях —
только ссылки (ADR-0011); локальные значения — в `.env` (не коммитится, агентам не
читать), имена ключей — в `.env.example` (без значений).

## Фичи через Spec Kit (SDD)

SDD-фича (`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` →
`/speckit-implement`) исполняется в ветке задачи, которая создаётся автоматически
— до записи артефактов в `specs/`:

| Момент | Действие | Результат |
|---|---|---|
| Начало `/speckit-specify` | Шаг 1: синхронизировать `main`, создать и запушить `feat/t-<NNN>-<slug>` (NNN — номер задачи по общему счётчику; номер фичи — только префикс каталога `specs/<NNN>-<slug>/`) | Ветка задачи в origin |
| `/speckit-specify` … `/speckit-tasks` | Коммиты артефактов (`docs: …`) в ветку задачи | SDD-артефакты в ветке |
| Завершение `/speckit-implement` | Коммит реализации (`feat: …`), проверки (`pnpm build` / `pnpm test`), пуш и открытие MR против `main` с описанием и evidence | Открытый MR |

- Хук `before_specify` spec-kit (`.specify/extensions.yml`) может создать ветку сам;
  если его нет или он не сработал, агент создаёт ветку по командам шага 1 — цикл
  от этого не отменяется.
- Артефакты `specs/<change>/` коммитятся в ветку задачи, не в `main`.
- MR открывается сразу по завершении `/speckit-implement` при зелёных проверках
  шага 3; merge — только человек. Push в `main` напрямую запрещён.
