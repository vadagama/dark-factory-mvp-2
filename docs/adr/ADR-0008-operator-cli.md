# ADR-0008: Операторский интерфейс — CLI-first

## Статус

Принято (инициализация репозитория, 2026-09-22).

## Основание

Notion v4: [«Хранение состояния, CLI и будущая Console» (стр. 10)](../sources/notion-v4/10-state-cli-console.md);
анализ §4 (Q3), §5; не переносится ADR-055 (оператор в DSH Web-плагине).

## Контекст

Оператор запускает Change'и, отвечает на вопросы фабрики, принимает решения гейтов,
разбирает сбои. Q3: CLI-first или веб-интерфейс в DSH.

## Решение

- **CLI-first (Q3)**: утилита `df` (`@dark-factory/cli`), без постоянного HTTP-сервера.
- **Инструментарий CLI — Commander + Clack, Ink позже**: детали — ADR-0013.
- **Прикладной API ядра**: `start / status / resume / cancel / submit-input /
  submit-decision`.
- **Ответ на вопрос**: `submit-input` принимает `questionId + responseId + версию
  вопроса` — фабрика отклоняет ответ на устаревшую версию вопроса.
- **Решение человека**: `submit-decision` — вход гейта `human-decision` (ADR-0005).
- **Идемпотентность по `commandId`**: повтор команды с тем же `commandId` и тем же
  содержимым возвращает прежнюю квитанцию; с изменённым — конфликт.
- **Один владелец состояния**: второй процесс `run`/`resume` — через IPC к владельцу,
  параллельных писателей SQLite нет (ADR-0002).
- **Console — после MVP**: снимки и события для UI уже предусмотрены моделью данных;
  веб-плагин DSH не является интерфейсом фабрики в MVP.

## Последствия

- MVP без фронтенда; автоматизация и скрипты работают тем же API.
- Все изменения состояния оператором идут через ядро и журналируются — ручных правок
  SQLite нет.
