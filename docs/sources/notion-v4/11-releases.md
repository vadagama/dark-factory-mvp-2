**Предлагаемое решение:** развивать Dark Factory как единый версионируемый продукт, внутри которого DSH — зафиксированный движок исполнения. Ядро, CLI, собственные плагины, процессы и инструкции на первом этапе хранить в одном репозитории и выпускать согласованными релизами.

Главная единица восстановления — релиз всей фабрики с известным составом компонентов и совместимым состоянием. Отдельные репозитории сами по себе такой возможности не дают.

Документ описывает проектируемое решение, а не уже реализованные возможности. Номера этапов и команды ниже — предложения для реализации.

## 1. Интеграция DSH

В архитектуре DSH расширение предусмотрено через плагины Cordis, bundles, profiles и конфигурационные patches. Есть headless-режим и SDK; TypeScript SDK использует соответствующую ему версию DSH. Это позволяет построить конфигурацию фабрики без постоянного изменения исходников движка.

Источник: [Архитектура DSH](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).

| Компонент | Ответственность |
|---|---|
| Dark Factory Core | Жизненный цикл задачи, переходы фаз, гейты, повторные попытки, состояние выполнения |
| CLI | Команды пользователя, диагностика, запуск процессов |
| DSH Adapter | Запуск движка, передача задания, получение событий и результата, отмена |
| DSH и собственные плагины | Агентная работа, инструменты, контекст, взаимодействие с моделями |
| Process Pack | YAML-процессы, MD-инструкции, skills, чек-листы, политики |
| Spec Kit Adapter | Работа со спецификациями и отдельными процедурами Spec Kit; Workflow Engine Spec Kit в v4 не используется |
| Release Launcher | Установка и переключение версий фабрики, восстановление после неудачного обновления |

Контракт фабрики с DSH принадлежит Dark Factory. Он включает запуск, наблюдение, отмену и получение структурированного результата. Внутренние объекты Cordis не должны проникать в ядро. Обновление DSH затрагивает прежде всего адаптер и плагины.

## 2. Репозитории

Для текущей стадии предлагается один основной monorepo для тесно связанных компонентов; знания и эксплуатационная конфигурация остаются отдельно.

| Репозиторий | Содержимое | Выпуск |
|---|---|---|
| dark-factory | Core, CLI, DSH Adapter, собственные DSH-плагины, процессы, skills, шаблоны, тесты, launcher | Единый релиз фабрики |
| dark-factory-knowledge | Спецификации и архитектурный baseline самой фабрики | Отдельная история; релиз ссылается на конкретный commit |
| dark-factory-gitops | Развёртывание и конфигурация окружений | Фиксирует выбранный релиз фабрики |
| dsh-fork — только при необходимости | Изменения непосредственно в исходниках DSH | Отдельная зависимость с точной версией |

Репозитории создаваемых продуктов и их знания остаются самостоятельными.

В основном репозитории достаточно каталогов `packages/core`, `packages/cli`, `packages/dsh-adapter`, `plugins/`, `processes/`, `skills/`, `templates/`, `tests/`, `releases/`.

Изменение контракта исполнения часто требует одновременно поправить ядро, адаптер, плагин и тест. Один commit и один MR сохраняют согласованность такого изменения.

По сравнению с ранее обсуждавшейся схемой из пяти репозиториев предлагается пока не выносить собственные тесно связанные плагины в отдельный dark-factory-plugins. Он оправдан позднее для расширений с независимыми владельцами и циклом выпуска. Логи запусков не должны определять структуру исходного кода.

## 3. Состав релиза

Релиз — неизменяемый собранный комплект, например Dark Factory 0.4.0:

- Core, CLI, адаптеры и собственные плагины.
- Точные версии DSH, SDK и всех транзитивных зависимостей.
- Зафиксированный профиль DSH и порядок конфигурационных patches.
- Процессы, prompts, skills, политики и шаблоны.
- Версии форматов состояния и контрактов.
- Манифест состава, контрольные суммы и результаты проверок.

На старте своим компонентам достаточно одного номера версии фабрики. Отдельный SemVer для каждого внутреннего пакета добавит работу без существенной пользы.

| Поле манифеста | Назначение |
|---|---|
| factoryVersion, sourceCommit | Идентичность релиза |
| artifactDigest | Точный исполняемый комплект |
| dshVersion, dependencyLockDigest | Точный движок и зависимости |
| processPackDigest | Процессы и инструкции |
| knowledgeCommit | Baseline, на котором выпущена фабрика |
| stateSchemaVersion | Совместимость состояния |
| harnessContractVersion | Совместимость адаптера |
| rollbackPolicy | Допустимый способ возврата |

Секреты в комплект не входят. Конфигурация окружения хранится отдельно; её версия или очищенный fingerprint фиксируется при запуске.

Откат использует сохранённый артефакт предыдущего релиза. Повторная сборка старого commit слабее: зависимости, инструменты сборки и внешние источники могли измениться.

## 4. Возврат к стабильной версии

Локально хранятся текущий стабильный комплект, предыдущий стабильный и кандидат. Launcher переключает активный комплект.

Предлагаемый интерфейс — команды потребуется реализовать:

```bash
df release install 0.4.0
df release activate 0.4.0
df release status
df release rollback
```

Launcher должен быть небольшим и запускаться независимо от основного CLI: поломка CLI не должна лишать команды восстановления. Нужен документированный ручной способ выбрать предыдущий комплект.

Последовательность обновления:

1. Установить новый комплект рядом со старым.
2. Проверить конфигурацию и совместимость состояния.
3. Остановить приём новых задач; активные завершить или корректно приостановить.
4. Создать согласованный checkpoint состояния.
5. Выполнить необходимые миграции и проверку запуска.
6. Переключить активный релиз.
7. При неуспехе вернуть предыдущий комплект и совместимое состояние.

Кандидат использует отдельные каталоги состояния, DSH home/profile и рабочие директории. Общий изменяемый пользовательский профиль DSH разрушает изоляцию релизов.

## 5. Состояние и внешние действия

Откат программы и откат её действий — разные операции.

| Что изменилось | Способ возврата |
|---|---|
| Core, CLI, плагины, инструкции | Переключить комплект релиза |
| SQLite или файловое состояние | Использовать обратную совместимость либо согласованный checkpoint |
| Сессии DSH | Проверить совместимость формата; при необходимости использовать сохранённую копию |
| Изменения в продуктовом репозитории | Отдельный revert или исправляющий MR |
| Уже развёрнутый продукт | Отдельный rollback релиза продукта |
| Созданные задачи, комментарии, внешние операции | Сверка фактического состояния и компенсирующие действия |

У DSH существуют миграции формата сессий. Наличие сохранённых поколений не означает, что старый движок сможет прочитать новое состояние. Совместимость сессий проверяется в сценарии отката.

Источник: [Хранение сессий DSH](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md#session-log).

Если новый релиз уже создал MR, возврат старого checkpoint не должен приводить к повторному созданию того же MR. Нужны идентификаторы операций, идемпотентность и reconciliation с внешними системами.

Для MVP прерванный запуск после отката продолжается с проверенной границы фазы, а не произвольно с середины агентного шага.

## 6. Последовательная разработка

1. Зафиксировать задачу и ожидаемый результат.
2. Создать отдельную ветку/worktree.
3. Внести изменения кода и связанных инструкций одним MR.
4. Выполнить быстрые локальные проверки.
5. Собрать кандидата из конкретного commit.
6. Проверить полный сценарий и откат.
7. Продвинуть тот же артефакт в стабильный релиз.

Основной цикл разработки и проверок выполняется локально. Перед объявлением релиза стабильным обязательна воспроизводимая проверка кандидата. GitLab CI можно сосредоточить на выпуске и развёртывании, сокращая зависимость каждого шага разработки от медленного CI.

Необходимые проверки:

- Контрактные: ядро корректно работает с адаптером, событиями, ошибками и отменой.
- Сценарные: небольшая задача проходит спецификацию, разработку, проверку и доработку.
- Восстановление: аварийное завершение, повторный запуск, установка кандидата и возврат предыдущего релиза.

Для логики ядра используются детерминированные заглушки движка. Для агентного качества — небольшой постоянный набор реальных задач. Изменение prompt или модели тоже способно нарушить работу фабрики и должно проходить соответствующие проверки.

## 7. Стабильные этапы

| Этап | Содержание | Условие стабильности |
|---|---|---|
| 0.1 — Исполнение | CLI → адаптер → DSH → структурированный результат | Повторяемый запуск, диагностика ошибок, отмена |
| 0.2 — Процесс | Фазы, артефакты, гейты, файловое состояние/SQLite | Возобновление с границы фазы после сбоя |
| 0.3 — Разработка | Worktree, Spec Kit, проверки, ограниченный цикл доработки | Одна небольшая фича проходит весь цикл |
| 0.4 — Релизы | Неизменяемые комплекты, launcher, checkpoints | Проверенный возврат на предыдущую версию |
| 0.5 — Параллельность | Несколько запусков, ограничения ресурсов, изоляция | Нет смешения состояния и рабочих каталогов |
| 0.6 — Доставка | VCS/MR, CI/CD, развёртывание | Раздельно проверены выпуск фабрики и выпуск продукта |

Точные зависимости и сохранение артефактов нужны уже с 0.1; в 0.4 автоматизируется полноценное управление релизами.

Собственные компоненты развиваются в monorepo, DSH обновляется отдельными контролируемыми изменениями, пользователю поставляется единый проверенный релиз фабрики. Стабильная фабрика может помогать разрабатывать следующую версию, но кандидат запускается изолированно и не изменяет работающую установку.
