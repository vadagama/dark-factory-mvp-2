**SQLite хранит оперативное состояние Dark Factory. YAML/Markdown описывают процесс и инструкции; файлы содержат артефакты; Git фиксирует версии. Ядро — единственный владелец переходов процесса.**

Этот документ задаёт проектируемый контракт MVP, а не утверждает наличие готовой реализации.

## 1. Источники истины

- SQLite: Change, Run, StageRun, Attempt, Workspace, вопросы, решения, внешние операции и компактный журнал событий.
- Версионированные файлы: процессы, политики, роли, инструкции, спецификации, baseline и исходники.
- Каталог неизменяемых артефактов: отчёты, манифесты, снимки входов и доказательства.
- DSH: собственная история сессий; фабрика хранит ссылки и наблюдаемые итоги.
- VCS, CI/CD и целевая среда: факты MR, pipeline и deployment. Локально хранится последнее наблюдение с observedAt.

Поисковые индексы и представления Console можно перестроить. Оперативную SQLite полностью восстановить из Git нельзя; она резервируется вместе с необходимыми артефактами. Workflow Engine Spec Kit и его state store в v4 не используются.

## 2. Один владелец состояния

В MVP один активный процесс ядра владеет всей локальной рабочей областью фабрики и может вести несколько Run. Он удерживает блокировку владельца, запускает исполнителей и изменяет доменное состояние короткими транзакциями.

Второй процесс run/resume не становится вторым планировщиком. Он передаёт команду владельцу через локальный IPC. Если владельца нет, команда получает блокировку, выполняет сверку и становится владельцем.

status читает согласованный снимок SQLite. cancel и submit-input обращаются к прикладному API владельца; при его отсутствии могут временно получить блокировку и записать ожидающее управляющее намерение без запуска агентной работы. Исполнение намерения продолжается следующим resume.

Отсутствие постоянного daemon в MVP не отменяет владение состоянием. Фоновый режим позднее использует тот же код ядра.

## 3. Идентификаторы и поколения

- stageId — логический этап в определении Process.
- stageRunId — выполнение этапа на фиксированном наборе входов и generation.
- attemptId — конкретная попытка исполнения внутри StageRun.
- executionKey — идентификатор одного запуска исполнителя; повтор доставки того же запроса использует прежний ключ.
- operationKey — отдельный ключ внешнего действия, например создания MR или доставки конкретного артефакта.

Изменение входов создаёт новую generation и новые зависимые выполнения. Старые accepted результаты остаются историей для прежних входов. Поздний результат старой попытки не принимает новую версию.

Входы, определения и решения закрепляются по хешам. Бюджет Run и счётчики циклов не обнуляются при смене generation.

## 4. Согласованность SQLite и файлов

Общей транзакции SQLite и файловой системы нет. Для регистрации артефакта:

1. Содержимое записывается во временный файл на том же файловом томе.
2. Проверяются схема, размер и хеш; файл закрывается и синхронизируется согласно требованиям надёжности.
3. Файл атомарно перемещается в конечное неизменяемое расположение, закрепляется запись каталога.
4. В короткой транзакции SQLite регистрируются Artifact и ссылка из результата.

Сбой до шага 4 оставляет неиспользуемый файл, который можно обнаружить и собрать после периода ожидания. Запись без доступного файла блокирует принятие результата; файл восстанавливается по хешу или проверка повторяется.

Публикация результата происходит только после проверки всех обязательных ссылок. Отчёт агента не перезаписывается под прежним идентификатором.

## 5. Внешние операции и восстановление

До вызова адаптера сохраняются тип операции, operationKey, хеш запроса, целевой объект и статус prepared. После ответа сохраняются внешний ID и наблюдаемый результат.

При неопределённом исходе статус unknown блокирует слепой повтор. Адаптер ищет выполненную операцию по доступным корреляционным данным. Если провайдер не обеспечивает однократность и факт нельзя установить, требуется решение.

resume сначала сверяет процессы, снимки, артефакты и внешние операции, затем разрешает новые попытки. Потеря heartbeat означает reconciling; interrupted требует подтверждения. Рабочий каталог нельзя передавать новому автору, пока прежний способен его менять.

## 6. Прикладной API и CLI

CLI и будущая Console используют одинаковые операции:

- start: проверить конфигурацию, закрепить версии и создать Run.
- status: вернуть снимок прогресса, блокировок, доказательств и внешних наблюдений.
- resume: восстановить наблюдение и продолжить разрешённую работу на закреплённых определениях.
- cancel: зарегистрировать запрос отмены и дождаться подтверждения остановки либо сохранить неопределённость.
- submit-input: передать ответ на questionId с уникальным responseId и ожидаемой версией вопроса.
- submit-decision: сохранить решение уполномоченного субъекта для точных хешей артефактов и политики.

Повтор команды с тем же commandId и тем же содержимым возвращает прежнюю квитанцию; другое содержимое с тем же ключом вызывает конфликт. Устаревшее решение не применяется к новой generation.

```bash
factory run --product tracker --flow feature --input intent.md
factory status <run-id>
factory resume <run-id>
factory cancel <run-id>
factory submit-input <run-id> --question <question-id> --file answer.json
```

Это проектируемые команды. Закрытие терминала не гарантирует продолжение работы. cancel не означает откат выполненного deployment.

## 7. События и Console

Доменное изменение и компактное событие записываются в одной транзакции SQLite. Event содержит eventId, sequence, runId, stageRunId/attemptId при наличии, type, occurredAt и ссылки на артефакты.

Console сначала получает снимок с последним sequence, затем читает события после него. Повторы устраняются по eventId; при недоступном курсоре загружается новый снимок. Полный event sourcing не нужен: текущие таблицы остаются источником состояния.

Текст модели и подробные tool logs — отдельная телеметрия. Их потеря не меняет решение гейта. Управляющие решения не извлекаются из текста терминала.

HTTP/SSE или другой транспорт Console выбирается позже; семантика снимка, команд и событий от транспорта не зависит.

## 8. Резервирование, сроки хранения и обновления

Для MVP резервирование выполняется при остановленном владельце и после прекращения изменений сохраняемых workspace: создаётся согласованный снимок SQLite и манифест необходимых файлов с хешами. Нельзя считать копию одного файла активной базы полноценным backup.

В backup входят закреплённые определения Run, принятые артефакты, доказательства, ссылки на Git revisions и необходимые данные восстановления DSH. Секреты сохраняются отдельно в предназначенном для них хранилище.

Временные worktree удаляются только после закрепления результатов. Диагностические логи могут иметь короткий срок хранения. Доказательства принятых выпусков хранятся по release-retention-policy и не удаляются общим правилом очистки через 30 дней.

Версия схемы SQLite и версии контрактов явные. Перед миграцией создаётся backup. Откат бинарника допустим только при совместимости схемы; восстановление старого backup требует сверки внешних операций, произошедших после него.

## 9. Проверка готовности MVP

Необходимы сценарии: повтор управляющей команды; вопрос и ответ в живой попытке; авария до/после регистрации файла; авария после создания MR; потеря связи с живым DSH; запоздавший результат старой generation; восстановление backup; несовместимая миграция.
