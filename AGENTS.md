# AGENTS.md — правила агентной разработки в этом репозитории

Правила конвейера Dark Factory v4. Архитектура — `docs/hld.md`, решения — `docs/adr/index.md`.

## Карта репозитория

```text
docs/
  adr/            # ADR-0001…0013 — архитектурные решения (index.md — реестр,
                  #   ADR-000-template.md — шаблон новых ADR)
  hld.md          # канонический HLD v4
  development-workflow.md  # git-цикл задачи (ветка → проверка → MR → merge)
  analysis/       # анализ инициализации (открытые вопросы §4)
packages/
  contracts/      # @dark-factory/contracts — канонические доменные контракты (zod)
  core/           # @dark-factory/core — ядро: домен, планирование, гейты, состояние
  plugin-api/     # @dark-factory/plugin-api — публичная поверхность расширений
  cli/            # @dark-factory/cli — операторский CLI `df`
  dsh-adapter/    # @dark-factory/dsh-adapter — HarnessAdapter на DSH SDK
plugins/          # плагины фабрики/DSH (появятся на 0.2+)
processes/ roles/ instructions/ skills/ gates/ policies/ schemas/
                  # декларативный процесс (появится на 0.2)
.specify/         # Spec Kit v1.0.6 (SDD-слой)
.agents/skills/   # speckit-* скиллы
```

## Команды

```bash
pnpm install          # установка зависимостей воркспейса
pnpm build            # сборка всех пакетов (tsc -b)
pnpm test             # тесты (vitest run)
pnpm test:watch       # тесты в watch-режиме
corepack enable       # если pnpm отсутствует (Node 24)
```

Требования: Node 24 (`.nvmrc`), pnpm 10 (corepack).

## Спецификация (Spec Kit / SDD)

Фичи ведутся через SDD-скиллы Zed: `speckit-specify` → `speckit-clarify` → `speckit-plan`
→ `speckit-tasks` → `speckit-implement` (+ `speckit-analyze`/`speckit-checklist`).
Артефакты живут в `specs/<change>/`, конституция — `.specify/memory/constitution.md`.
Процедуры Spec Kit исполняются как этапы процесса фабрики (ADR-0007).

Каждая SDD-фича автоматически открывает git-цикл задачи: `/speckit-specify` начинается
с создания и пуша ветки задачи от свежего `main` (до записи артефактов в `specs/`),
завершение `/speckit-implement` — открытием MR против `main`. Модель ветвления —
trunk-based (короткоживущие ветки); детали — `docs/development-workflow.md`.

## Скиллы агентов (роли)

Кроме SDD-скиллов проекта выше, доступны общие ролевые скиллы агента — глобальные,
в `~/.agents/skills/<имя>/SKILL.md`. Роль задаёт режим работы над задачей, но не
отменяет правила этого файла и границы ADR. В терминах фабрики это тот же принцип,
что и в декларативном процессе: роль — конфигурация, а не сущность (ADR-0003/0004).

| Скилл | Роль | Когда использовать |
|---|---|---|
| `develop` («Carl») | staff-инженер | Любые правки кода: исследование кодовой базы, реализация по паттернам проекта, dev-тесты, устранение находок ревью |
| `architect` («Stuart») | архитектор | Проектирование и ревью архитектуры: границы и контракты, ADR, tech debt, NFR, декомпозиция на вертикальные срезы |
| `product` («Kevin») | продакт | Замысел, требования и скоуп, user stories с критериями приёмки, MVP, roadmap |
| `design` («Bob») | UX/UI | Пользовательские флоу, состояния экранов, маппинг на UI-kit, доступность, приёмка UI |
| `quality` («Phil») | QA | Стратегия тестирования, независимая приёмка по AC, quality gates, регресс, валидация NFR |
| `ci-cd` («Tim») | CI/CD | Пайплайны (verify/typecheck/lint/test), релизы, деплой и откат, git-цикл задачи (ветка, коммиты, PR/MR), smoke |
| `infrastructure` («Dave») | инфраструктура | IaC: Terraform/Kubernetes/Helm, сети, IAM, окружения; план/apply, идемпотентность, drift-контроль |
| `operation` («Jerry») | эксплуатация | Наблюдаемость (метрики/логи/трейсы), SLI/SLO, алертинг, ранбуки, инциденты |
| `security` («Mel») | безопасность | Threat modeling, ревью IAM/данных/границ доверия, SAST/SCA/секреты; подключается к risky-изменениям (ADR-0011) |
| `yandex-cloud-engineer` | Yandex Cloud | Облачная инфраструктура Yandex Cloud как код (Terraform, GitLab CI/CD) — только для YC-проектов |
| `create-skill` | мета | Создание/обновление скиллов (SKILL.md) |

Типичные связки: фича — `product` → (`design`, `architect`) → `develop` → `quality` →
`ci-cd`; инфраструктура — `architect` → `infrastructure` → `ci-cd` → `operation`;
risky-изменения — `security` поверх основного маршрута.

## Ветки и коммиты

- Ветки задач: `<type>/t-NNN-<slug>`, где `<type>` — характер изменения:
  `feat/`, `fix/`, `chore/`, `docs/`, `refactor/`, `test/`
  (например `feat/t-001-core-domain`, `fix/t-007-gate-verdict`).
- Модель ветвления — trunk-based: короткоживущие ветки ответвляются от свежего
  `main` и вливаются обратно только через MR; долгоживущие ветки разработки
  не используются, `main` всегда стабилен и готов к релизу.
- `main` всегда стабилен: push в него напрямую запрещён; merge — только человек.
  Автономный merge появится позже и только для продуктовых репозиториев, по 5 условиям
  и политикам риска (`ADR-0006`, `ADR-0012`).
- Git-цикл задачи (ветка до реализации → проверка → MR → merge человеком):
  `docs/development-workflow.md`.
- Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`.
  Примеры из истории: `docs: add v4 architecture comparison…`, `chore: bootstrap Spec Kit…`.
- Изменение архитектурных решений — новый ADR/amendment (шаблон:
  `docs/adr/ADR-000-template.md`), не молчаливая правка кода.

## Жёсткие правила агента

- Сначала читай `docs/` (`hld.md`, `adr/`) — там контекст проекта; не переспрашивай
  то, что уже задокументировано.
- Язык: документация и общение с пользователем — русский; код, идентификаторы,
  коммиты — английский.
- Каждое изменение кода валидировать фактически: `pnpm build`, `pnpm test`,
  диагностика по изменённым файлам. Не заявлять о пройденной проверке, если она
  не запускалась.
- Не чинить попутно несвязанные баги — упомянуть их в финальном сообщении.
- Не трогать файлы и изменения, созданные не тобой, без явного запроса пользователя.
- Секреты — никогда в коде и в git (`ADR-0011`): локальные значения — в `.env`
  (не коммитится; агентам запрещено читать, выводить или копировать его содержимое),
  имена ключей — в `.env.example` без значений; в декларациях — только ссылки.
- Коммиты и пуши — только в ветку задачи (`docs/development-workflow.md`); вне цикла
  задачи не коммитить без явной просьбы пользователя.
- Новая фича через Spec Kit начинается с автоматического создания ветки задачи
  (до записи артефактов `specs/`) и завершается открытием MR после
  `speckit-implement`; merge — только человек (`docs/development-workflow.md`).

## Definition of Done

1. `pnpm build` и `pnpm test` — зелёные.
2. Изменение не нарушает ADR (границы слоёв, контракт гейтов, владелец состояния).
3. Новая функциональность покрыта тестами; контрактные типы — в `contracts`.
4. Обновлены затронутые документы (`docs/hld.md`, ADR) — для изменений поведения.
5. Нет секретов в коде и декларациях — только ссылки.

## Архитектурные границы (не нарушать)

- **Ядро не импортирует SDK DSH** и любые внешние исполнители — только через адаптеры
  (`ADR-0001`). SDK-типы не протекают в домен.
- **Единственный владелец состояния** — `core` (SQLite); CLI и плагины пишут только через
  API ядра (`ADR-0002/0008`).
- **YAML — не язык программирования**: нет выражений/eval в процессах, гейтах, политиках
  (`ADR-0004/0005`).
- **Гейт — ровно 4 исхода**: `passed / rework_required / blocked / decision_required`;
  `GateResult` не выбирает следующий этап (`ADR-0005`).
- **retry ≠ rework**: технические повторы и циклы доработки не смешиваются (`ADR-0003`).
- **`completed` от DSH ≠ принятый результат**: принятие — только через гейт (`ADR-0005`).
- **Плагины не меняют таблицы ядра**, не выставляют `accepted`, не запускают этапы
  (`ADR-0010`).
- **Секреты вне git** — ссылки в декларациях, подстановка в момент исполнения (`ADR-0011`).
- **DSH не выдаются токены merge/production**; merge/доставка — только через адаптеры ядра
  (`ADR-0006`).
